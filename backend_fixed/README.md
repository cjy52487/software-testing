# 测试说明 README.md

> 
> 项目：外卖后台接口自动化测试
> 测试模块：组员A‑用户注册、用户登录、商家菜品管理

- 自动化用例总数：**22条（TC‑001 ~ TC‑022）**
- 测试对象接口：
  - 用户注册：`POST /api/user/register/test`
  - 用户登录：`POST /api/user/login`

# 发现有效缺陷汇总

## BUG‑001 用户注册接口：未校验手机号必须11位

- **缺陷现象**：注册接口允许传入10位、12位非标准11位手机号，仍然注册成功并写入数据库。
- **预置条件**：后端服务正常启动，数据库可访问。
- **复现步骤**
  1. 请求接口 `POST /api/user/register/test`
  2. 请求体传入合法用户名、合法密码，手机号分别传入`1381234567`(10位)、`138123456789`(12位)
  3. 发送请求，观察返回结果
- **预期结果**：注册失败，返回提示“手机号必须是11位数字”。
- **实际结果**：返回`status:200`，提示注册成功，用户入库。
- **严重等级**：高(High)
- **自动化用例**：TC‑002、TC‑003
- **修复方案**：注册接口增加正则校验手机号，正则：`r'^\d{11}$'`。
- **修复验证**：修复后传入10/12位手机号返回业务错误码；传入合法11位手机号可正常注册；pytest中TC‑002、TC‑003执行PASS。

## BUG‑002 用户注册接口：新增菜品成功响应不返回dish_id

- **缺陷现象**：商家调用新增菜品接口`POST /api/dishes`添加菜品成功后，返回json不携带`dish_id`，无法直接获取新增菜品主键，自动化编辑、删除菜品无法拿到目标ID。
- **预置条件**：商家账号token有效，账号绑定有效shop_id。
- **复现步骤**
  1. 携带商家token，请求`POST /api/dishes`，传入合法菜品参数。
  2. 查看接口返回响应。
- **预期结果**：返回`status:200`，同时在`data.dish_id`返回新增菜品主键ID。
- **实际结果**：返回`{"status":200,"msg":"菜品添加成功","image_url":"xxx"}`，缺少`dish_id`字段。
- **严重等级**：中(Medium)
- **自动化用例**：TC‑021、TC‑023（编辑、删除依赖新增返回dish_id）
- **修复方案**：菜品插入数据库commit之后，查询本次新增记录的`dish_id`，放到返回`data`对象中返回。
- **修复验证**：新增成功响应包含`data.dish_id`；自动化用例可以拿到id，完成后续编辑、删除流程，TC‑021、TC‑023 PASS。

## BUG‑003 商家新增菜品接口：price=0被识别为空值

- **缺陷现象**：商家新增菜品传入价格为`0`（用于赠品/免费菜品），接口错误提示“菜品价格不能为空”，新增失败。Python中`0`被`if not price`判定为假。
- **预置条件**：商家token有效，合法shop_id。
- **复现步骤**
  1. 请求`POST /api/dishes`，price传数字0，其他字段合法。
- **预期结果**：价格0合法，菜品新增成功。
- **实际结果**：返回`status:400`，提示菜品价格不能为空。
- **严重等级**：中(Medium)
- **自动化用例**：TC‑018
- **修复方案**：将判空逻辑由`if not price`修改为`if price is None`，只拦截字段缺失，允许数值0。
- **修复验证**：price=0可以正常新增菜品，TC‑018执行PASS。

## BUG‑004 商家新增菜品接口：未拦截负数价格

- **缺陷现象**：新增菜品时price传入负数，接口没有拦截，允许保存负数价格。
- **预置条件**：商家token有效，合法shop_id。
- **复现步骤**
  1. 请求`POST /api/dishes`，price传入`-5`，其他参数合法。
- **预期结果**：新增失败，提示菜品价格不能为负数。
- **实际结果**：菜品新增成功，数据库保存负数价格。
- **严重等级**：中(Medium)
- **自动化用例**：TC‑019
- **修复方案**：接口增加判断：`if price <0`，直接返回400业务错误。
- **修复验证**：负数价格被拦截；正数、0价格可以正常新增；TC‑019 PASS。

## BUG‑005 商家编辑菜品接口：缺少菜品归属权限校验

- **缺陷现象**：商家可以编辑不属于自己店铺的菜品ID，没有做归属校验。
- **预置条件**：存在两个不同商家及其店铺、菜品；当前登录商家token。
- **复现步骤**
  1. 使用商家A的token，调用`PUT /api/dishes/<dish_id>`，传入属于商家B的菜品dish_id，参数合法。
- **预期结果**：返回403权限不足，禁止编辑。
- **实际结果**：可以修改其他商家的菜品数据。
- **严重等级**：高(High)
- **自动化用例**：TC‑022
- **修复方案**：更新接口SQL查询，JOIN shop表校验`shop.owner_username`等于当前登录商家用户名；查询不到记录直接返回403无权编辑。
- **修复验证**：操作别人的菜品返回403；操作自己的菜品编辑成功，TC‑022 PASS。

## BUG‑006 注册接口原始缺陷（已修复）

> 
> 原接口无密码复杂度校验，允许密码缺少大写、小写、数字、长度非法；已在后端增加正则`^(?=.*[a-z])(?=.*[A‑Z])(?=.*\d).{6,12}$`完成修复。

- 涉及用例：TC‑005、TC‑006、TC‑007、TC‑008、TC‑011
- 修复验证：非法密码被拦截；合法密码可注册，对应用例全部PASS。

## 测试备注

1. 数据库清理：pytest会生成大量`test_u_xxxx`测试账号；Navicat执行SQL优先删除测试账号，保留业务商家账号。

```
DELETE FROM user_msg WHERE id IN (SELECT id FROM user WHERE username LIKE 'test_u_%');
DELETE FROM user WHERE username LIKE 'test_u_%';
COMMIT;
```

2. 执行前确认`config.py`中账号、密码、`MERCHANT_SHOP_ID`与MySQL数据库保持一致。
